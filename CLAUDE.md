# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Static, dependency-free single-page app (UI text in Spanish) that shows an academic timetable for the 2026–27 course (Wednesday evening classes, Sep 2026 – Jun 2027) for two student groups (A/B), and tracks exams, notes, and absences against an 80% minimum-attendance rule.

- `favicon.svg`: page icon, the same amber calendar as the Android launcher icon (`android/res/drawable/ic_launcher_fg.xml`); keep both drawings in sync. The page `<title>` is "Horario 2º ASIR".
- `horario.html`: markup for all views plus the add-record `<dialog>`. It wires behavior through inline `onclick`/`oninput`/`onsubmit` handlers that call global functions in `js/script.js`.
- `js/script.js`: all data and logic, as plain globals (no modules). Loaded at the end of `<body>`; it calls `init()` directly on load.
- `css/styles.css`: warm dark theme built on the `:root` tokens. Amber (`--accent`) is the only accent and is reserved for selection and the primary action. Module colors are `--color-<code>` (oklch, same lightness) and `MODULES[*].color` references them as `var(--color-xxx)`; record types use `--absence`/`--exam`/`--note`. Icons are an inline SVG sprite in `horario.html` (`<use href="#i-…">`); no emoji.
- Two themes: dark (default brown) tokens on `:root`, day mode overrides on `:root[data-theme="light"]`. An inline `<head>` script sets `data-theme` before first paint from `localStorage['horario_theme']`, falling back to `prefers-color-scheme`; `setTheme(theme, button)` (the Noche/Día switch in the side menu) saves the choice and switches with a View Transitions circular reveal from the pressed button (color fade fallback); on `(pointer: coarse)` it uses `themeWipe()` instead, a fixed circle in the new `--bg` color that grows with `transform` only, applies the theme under `.theme-instant` (transitions off) while covered, then fades out (it is appended inside `#menuDrawer` while that is open, so it stays above the top layer), because the clip-path reveal stutters on phones. For the same reason, touch devices drop the per-chip `translateZ(0)` layers and the intro blur. Module colors derive from `--mL`/`--mC` so each theme only changes lightness/chroma, except `--color-imw` (yellow), `--color-ade` (lime), `--color-eib` (orange) and `--color-soj` (salmon), which are fixed bright values (at the shared lightness they came out khaki/olive/brown/brick; EIB also has a day-mode value); in day mode their chips use `--m-ink`/`--m-tint` (dark text of the same hue, stronger tint, set via `.chip[style*="--color-xxx"]`) because those bright colors aren't legible as text on light backgrounds. Layout: above 1500px the table sits beside two side-by-side panels (Asistencia | Registros), whose top is aligned with the table itself by `alignSidebar()` (sets `--align` on `.sidebar`; measured with `getBoundingClientRect` against `#viewGrid`, since Firefox treats the animating view as `offsetParent`); below that the panels drop under the table. Use `--accent-text`, not `--accent`, for amber text so it stays legible in day mode. Recessed areas inside elements (form fields, table break row) use `--inset`, not `--bg`, so changing the page background never recolors elements. The Asistencia/Registros boxes use `--panel` (= `--surface` in dark mode, a warm off-white `#f6eee2` in day mode instead of near-pure white), with `--bar-track` for the empty part of their bars and `--panel` for the 80 % tick. The "Trimestre" table has its own tokens (`--table-bg`, `--table-head`, `--table-holiday`): dark mode maps them to the surface tokens, and day mode uses a warm bone body with a caramel header band darker than `--bg` (keep them distinct from the page background).
- On touch devices (`pointer: coarse`) the page behaves like an app: no tap highlight, and no text selection or callout outside inputs.
- Fonts (Geist, Geist Mono) are bundled in `fonts/` (latin + latin-ext woff2, SIL OFL) and declared in `css/fonts.css`, so the app works offline; mono is only for times, dates, percentages and module codes.

There is no build, package manager, linter, or test suite. To run it, open `horario.html` in a browser or serve the directory (for example `python3 -m http.server`).

## Database design (`db/`, `docs/modelo-datos.md`)

A SQLite (≥ 3.37, `STRICT` tables) model for the whole CIFP, not yet used by the app: `db/schema.sql` (tables + triggers for rules SQLite can't express as `CHECK`: no overlapping classes per room/teacher/group, no classes in breaks or holidays, absences only for enrolled students, approving a justification marks absences justified), `db/views.sql` (`v_asistencia` / `v_asistencia_personal` reproduce `renderAttendanceBars()` over the whole course), and `db/seed_2asir.sql`, **generated** from the data tables of `js/script.js` by `node db/generar_seed.js` — rerun it whenever `MODULES`, `TIME_SLOTS`, `CALENDAR_DATES` or `SCHEDULE_A/B` change. `python3 db/pruebas.py` loads everything in memory and runs the checks (exit 1 on failure). Official absences (`falta`, teacher) and the student's own tracking (`falta_personal`) are separate tables; a class can belong to several groups (`sesion_grupo`, 4 joint A+B classes). SQLite has no roles, so per-role access is the API's job: the permission matrix is in `docs/modelo-datos.md`.

## Android app (`android/`)

`android/build.sh` packages the web into `Horario.apk` (a single-Activity WebView loading `file:///android_asset/www/horario.html`) with plain SDK tools, no Gradle: it copies `horario.html`, `favicon.svg`, `css/`, `js/`, `fonts/` into assets, then runs aapt2, javac, d8, zipalign and apksigner. It expects JDK 17 under `~/.local/opt/jdk-17*` and `~/Android/Sdk` with `platforms;android-34` and `build-tools;34.0.0`. Rerun it after any web change; each run auto-increments the version code stored in `android/version.txt` so installs over the previous APK are treated as updates. The first run creates `android/horario-release.jks` + `keystore.properties`: updates must be signed with that same key, and neither file should be shared. The page calls `window.AndroidApp.setTheme(theme)` (when present) so the system bars follow the day/night theme; the Back button closes an open `<dialog>` or `#ctxMenu` before exiting. No INTERNET permission: everything is local. Reminders: `syncReminders()` (called from `saveData()` and `init()`) sends `AndroidApp.syncReminders(json)` the full list of pending exam/task reminders (`times` at `REMINDER_HOUR` on each chosen day, `due`, `repeat` for tasks). `Reminders.java` stores it in SharedPreferences and keeps one exact alarm per record; tasks repeat daily from the first reminder until done. The notification has "Posponer" (1 h) and, for tasks, "Entregada", which queues the id; the page picks the queue up with `applyNativeActions()` → `AndroidApp.takeDoneIds()` (on load and on `onResume`) and sets `status: 'done'`. `BootReceiver` reschedules after reboot or app update. Haptics: `haptic(kind)` in the page calls `AndroidApp.haptic()`, which plays Android's predefined effects (`tap` → `EFFECT_TICK` on a per-hour absence, `press` → `EFFECT_CLICK` when a long press opens the menu, `strong` → `EFFECT_HEAVY_CLICK` on a whole-day absence; one-shot fallback below API 29, `USAGE_TOUCH` from API 33 so the system touch-feedback setting applies); outside the app it falls back to a few ms of `navigator.vibrate` on touch screens.

## Data model (js/script.js)

These hardcoded tables are all aligned **by index**, so edits must keep them in sync:

- `CALENDAR_DATES`: one entry per Wednesday class date (39 entries). `monthIdx` is an index into `MONTHS_DATA` (0 = Sept 2026 … 9 = June 2027), **not** a JS month number. `dayNum` must match the day in `date`. Holiday entries carry `holiday`.
- `SCHEDULE_A` / `SCHEDULE_B`: parallel to `CALENDAR_DATES` (same length). Each entry is either `null` (no class or holiday) or a 5-element array of module codes, one per non-break slot in `TIME_SLOTS` (`key` 0–4). A slot can also be `null`.
- `MODULES`: module code → name, teacher, room, color. Every code used in the schedules must exist here and have a matching `--color-*` variable in `css/styles.css`.
- `MONTHS_DATA`: month grid metadata. `startDayOfWeek` is Monday-based (0 = Mon) and hand-computed; verify against `new Date()` when editing (all ten were once off by one).
- `userEvents`: user data persisted in `localStorage` under the key `academic_events_dark`, shaped as `{ [dateIndex]: [{ type: 'exam'|'task'|'absence'|'note', module, text, slot?, …typeFields }] }`. `slot` (a `TIME_SLOTS` key 0–4) is set only by clicking a chip in the "Trimestre" table (`toggleSlotAbsence()`); such an absence counts exactly 1 hour for its module. Clicking a date in the table header marks or clears all that day's hours at once (`toggleDayAbsence()`). Right-clicking a chip (or a ~480ms touch long-press, `startLongPress()`; the native `contextmenu` is ignored for touch and the release click is swallowed so it can't hit the menu) opens a custom context menu (`openSlotMenu()`; the same gesture on a table header date or a "Mes" day opens `openDayMenu()`, which asks for the kind and then the subject via `showModulePicker()`, and on a "Día" class row opens `openBlockMenu()`; `MENU_TARGETS` / `openMenuFor()` route contextmenu and long-press at document level; pressing the element whose menu is open only closes it, `onMenuOutside()` + `swallowNextClick()` drop that click) that creates per-hour `exam` (`topics`, `weight` %, `grade` /10), `task` (`title`, `desc`, `weight`, `status` `'pending'|'done'`, `grade`) or `note` records via the `#slotDialog` form (`openSlotDialog()` / `saveSlotRecord()`); `text` always holds the one-line summary shown in lists. Exam/task records also carry a stable `id` (`newRecordId()`, assigned lazily to older records) and `notify` + `notifyDays` (days before, default `[3]`), edited in the `.notify-fields` block of `#slotDialog`, which only shows inside the Android app (`html.is-app`). Records created from the day menu carry `byDay: true`; exams with it (`isDayExam()`) put their dot on the day number (`dayDot()`, table header and "Mes" grid) instead of on the chip (`chipRecords()` excludes them). A dot turns green and stops pulsing when `recordsDone()` holds: every exam has a grade and every task is done (notes don't block it, but a notes-only chip stays yellow). Chips with any exam/task/note show a single pulsing yellow corner dot, and hovering (or keyboard focus) shows the `#chipTip` bubble listing those records (`showTip()`). Because events are keyed by position in `CALENDAR_DATES`, inserting or reordering dates silently reassigns existing user data to other dates.
- `personalEvents`: personal tasks and notes on days without classes (any "Mes" day not in `CALENDAR_DATES`, plus holidays and days whose schedule is empty), persisted separately in `localStorage['horario_personal']` as `{ 'YYYY-MM-DD': [{ type: 'task'|'note', text, title?, desc?, status?, id, notify?, notifyDays? }] }`, with no `module`, `slot`, `weight` or `grade`. `saveData()` persists both stores. In "Mes" those days are `button.month-day.is-free` (or class-less `CALENDAR_DATES` buttons) carrying `data-iso`; a mouse click or the context-menu gesture opens `openPersonalMenu()` (`hasClasses()` decides; on touch a plain tap does nothing, only the long press opens it), which edits through the shared `#slotDialog` via `openPersonalDialog()` (`showRecordDialog()` is the common part; `.is-personal` hides weight/grade and swaps `[data-personal]` labels to "Detalles"/"Hecha"). Up to three records are written inside the day cell (`personalList()`, hidden on phones where only `dayMarks()` remain). Registros merges them by date (`deletePersonal()`); in the table's sub-tabs a personal date belongs to the range that starts before it, up to the next range's first date. Personal tasks with `notify` are sent to Android too (`code: ''`, due 23:59; `Reminders.java` titles them "Entrega …" without a subject).

Hardcoded date strings (`'23 Sep'`, `'13 Ene'`, `'20 Ene'`, `'14 Abr'`, `'21 Abr'`, `'2 Jun'`) define the three matrix sub-tab ranges in `renderMatrix()` and must match `CALENDAR_DATES[*].date` exactly. The button labels in `horario.html` repeat them.

## Rendering flow

State lives in globals (`currentGroup`, `selectedMonthIndex`, `selectedDateIndex`, `currentMatrixSubTab`, `filterModule`). Each view has a `render*()` function that rebuilds its container from scratch through `innerHTML`, so nothing is diffed. After any state change, call the render functions for the affected views:

- `saveData()` persists `userEvents` and re-renders every view that depends on events.
- The page has no title or search box: the header (`.topbar`) holds only the tabs and the menu button (`#menuBtn`), which opens `#menuDrawer`, a modal `<dialog>` sliding in from the right (`openMenu()` / `closeMenu()`, the latter runs the exit animation). It contains the group switch, the theme switch and the usage help.
- `switchGroup()` re-renders the views that depend on the schedule and saves the group in `localStorage['horario_group']`, read back on load (`loadGroup()`, `syncGroupLabels()`).
- `switchTab()` toggles `.is-shown` on `#viewMonthly`, `#viewWeekly`, `#viewGrid`, `#viewModules`, derives the tab button id as `'tab' + Capitalized(tab)`, and moves the sliding `.tab-indicator`.
- "Trimestre" (`viewGrid`) is the first tab and the default view. Its usage instructions are not shown inline but in the "Cómo se usa" section of `#menuDrawer`. `.hint-mouse` / `.hint-touch` spans swap the wording (clic / toca, clic derecho / mantén pulsada) under `(hover: none) and (pointer: coarse)`.
- On load, the selected date/month is the next upcoming class (`nextClassIndex()`), not the first date, and the table opens on the sub-tab containing it (`subTabOf()` / `setMatrixSubTab()`). On touch devices only, `scrollMatrixToToday()` (on load, after fonts load and on sub-tab change) scrolls `.table-wrap` so the first date column next to "Hora" is the last non-holiday class before today (measured as `offsetLeft` distance from the first date column, since the cells' `offsetParent` is the body); `switchTab()` keeps the table's `scrollLeft` when leaving and returning to "Trimestre".
- Live progress (`#liveClass`, under the "Trimestre" table): on a class day, `tickLive()` runs every second (`startLive()`, skipped while the page is hidden, rerun on `visibilitychange`) and `livePhase()` derives the current `TIME_SLOTS` segment from the clock: `class` (module color), `break`, `free` (null slot) or `done` (after the last class, 100 % in `--done` until `DAY_END` 23:59). It is hidden before the first class and on days without classes. The card is only rebuilt when the phase key changes; the fill advances via `--p` with a 1s linear transition. Entering `done` calls `celebrateDay()`, which runs `launchFireworks()` (a self-removing full-screen `<canvas class="fireworks">`, colors from the record/accent tokens, skipped under reduced motion) once per date, remembered in `localStorage['horario_fireworks']`; the "Otra vez" button replays it. A temporary test bar (`.sim-bar`, top of `.app`, marked with a comment in `horario.html`) calls `simulateAt(time)`, which sets `clockOffset` so `liveNow()` runs from that time on the next class day (`null` restores the real clock); in simulation the fireworks always fire and don't touch `horario_fireworks`.
- Day numbers in the table header, the "Mes" grid and the "Día" tab (date list and `#selectedDateTitle`, via `.date-n`) are colored by state: the next class in amber (`is-next`), past class days in green (`is-past`, `--done`), and days where every class hour counts as an absence in red (`is-absent`, `--absence`, past or future; it wins over the other two). `dayState()` computes it.

Attendance (`renderAttendanceBars()`): each module's total hours and absences are always counted over the whole course from the group's schedule (a module split across sub-tabs, like SOJ, must not jump to 0 % for one absence in the sub-tab where it has a single class); the current range (the table's sub-tab) only decides which modules are listed, those with a class in it. An absence tied to a module subtracts that module's slots for that day (or 2 if the module has none that day). An absence with no module subtracts one hour from every module scheduled that day. In the "Día" tab the panel only lists the modules scheduled on `selectedDateIndex` (percentages still count the whole course) and `selectDate()` re-renders it. `slotAbsence()` tells the table whether a cell is covered by a per-hour absence (toggleable) or by one of these broader ones (click only shakes and shows a toast).

`filterModule` is always `null` since the search box was removed; renderers still add `.is-dimmed` to anything that isn't that module when it is set.

The Registros panel lists the events of the current range (the table's sub-tab range on "Trimestre", all dates elsewhere). Its three filter tiles call `setRecordFilter('exam'|'task'|'note')`, which sets `recordFilter` so `renderSidebarNotes()` shows only that type; pressing the active one again resets it to `null` (show everything, absences included). Per-hour absences stay one event per slot in storage, but `groupDayEvents()` shows 2+ consecutive slots of the same day (the break doesn't split a run) as one entry, "Falta del día" when it covers every class slot and "Faltas seguidas" otherwise, listing each module with its session count and no times; its delete button removes the whole run (`deleteEvents()`). The "Día" view's event list uses the same grouping. Each Registros row shows the date large and bold on the left as `7 SEP` (`recordDate()`), with the subject chip (or the "Personal" tag) under it; `.record-when` is a two-row grid sharing `--rec-row`/`--rec-gap` with `.record-head` and the first line of `.record-text`, so the date lines up with the type and the chip with the text; to the right, a `.record-head` line with the type (`recordMeta(label)`) followed by `— Pendiente`/`— Entregada` for tasks or `— Nota x` for graded exams (`recordStatus()`, green when done), then the comment and a detail line with weight and task grade (`recordExtra()`), with no times; a single per-hour absence reads "1 sesión" instead of its stored `Hora …` text. The panel has no add button: records are created from the table, so the `#eventModal` add form is no longer reachable from the UI.

## Motion

- Entrance animation plays once per page load: an inline `<head>` script adds `html.is-intro` (skipped under `prefers-reduced-motion`), CSS keys the intro keyframes off it, and `init()` removes it after 1.5s. Content is visible by default if JS fails.
- Re-renders replace `innerHTML`, so state-change animations are re-triggered with `replay(el, 'is-swapping')`. Attendance bars keep their previous `--p` for one frame so width changes animate via `transform: scaleX`.
- The add-record form is a native `<dialog>`; close through `closeAddModal()` so the exit animation runs.
