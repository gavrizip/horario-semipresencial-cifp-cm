# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Static, dependency-free single-page app (UI text in Spanish) that shows an academic timetable for the 2026–27 course (Wednesday evening classes, Sep 2026 – Jun 2027) for two student groups (A/B), and tracks exams, notes, and absences against an 80% minimum-attendance rule.

- `favicon.svg`: page icon, the same amber calendar as the Android launcher icon (`android/res/drawable/ic_launcher_fg.xml`); keep both drawings in sync. The page `<title>` is "Horario 2º ASIR".
- `horario.html`: markup for all views plus the add-record `<dialog>`. It wires behavior through inline `onclick`/`oninput`/`onsubmit` handlers that call global functions in `js/script.js`.
- `js/script.js`: all data and logic, as plain globals (no modules). Loaded at the end of `<body>`; it calls `init()` directly on load.
- `css/styles.css`: warm dark theme built on the `:root` tokens. Amber (`--accent`) is the only accent and is reserved for selection and the primary action. Module colors are `--color-<code>` (oklch, same lightness) and `MODULES[*].color` references them as `var(--color-xxx)`; record types use `--absence`/`--exam`/`--note`. Icons are an inline SVG sprite in `horario.html` (`<use href="#i-…">`); no emoji.
- Three themes: dark (default brown) tokens on `:root`; day mode on `:root:is([data-theme="light"], [data-theme="rosa"])`, so the pink "Rosa" theme inherits every light-mode legibility rule (module chips, `--m-ink`) and `:root[data-theme="rosa"]` only swaps the palette (#f70071 · #ff1b82 · #ff5aa4 · #ff96c5 · #ffc0dc, plum text). Rosa is hidden: the menu only shows Noche/Día, and holding «Día» for 3 s (`pointerdown` timer in `init()`, `.is-holding` fill, `swallowNextClick()` so the release doesn't switch back to day) calls `rosaIntro()` (the unlock sequence, ~4.5 s, skipped under reduced motion: menu closes, a plum `.rosa-intro` veil with a canvas rain of thin yellow 4-point stars in three depths plus pointer parallax, the theme is applied behind the veil at 1.3 s, the bow and «Modo rosa» letters pop in at 1.45 s, and at 2.7 s the veil zooms out while `html.rosa-reveal` makes the app enter by layers with bouncy keyframes and `floatHearts()` sends hearts up); while active the Día button shows a heart and stays selected. `--bow` (the bow mask) lives on `:root` so the intro and the record marks share it. Rosa-only effects: absences burst into star sparkles (`rosaSparkles()`, WAAPI on fixed `.sparkle` spans, replacing the red `is-pop-on` ring), the record dot (`.chip-dot`, `.day-dot`, help) becomes a swaying pink bow via a CSS mask (green when done), and `launchFireworks()` bursts along a heart curve drawing each spark as a small heart. Each theme's page background lives in `THEME_BG` (`js/script.js`), repeated in the `<head>` script and in `MainActivity.applyBars()` (Android bars: dark icons for light and rosa). An inline `<head>` script sets `data-theme` before first paint from `localStorage['horario_theme']`, falling back to `prefers-color-scheme`; `setTheme(theme, button)` (the Noche/Día switch in the side menu) saves the choice and switches with a View Transitions circular reveal from the pressed button (color fade fallback); on `(pointer: coarse)` it uses `themeWipe()` instead, a fixed circle in the new `--bg` color that grows with `transform` only, applies the theme under `.theme-instant` (transitions off) while covered, then fades out (it is appended inside `#menuDrawer` while that is open, so it stays above the top layer), because the clip-path reveal stutters on phones. For the same reason, touch devices drop the per-chip `translateZ(0)` layers and the intro blur. Module colors derive from `--mL`/`--mC` so each theme only changes lightness/chroma, except `--color-imw` (yellow), `--color-ade` (lime), `--color-eib` (orange) and `--color-soj` (salmon), which are fixed bright values (at the shared lightness they came out khaki/olive/brown/brick; EIB also has a day-mode value); in day mode their chips use `--m-ink`/`--m-tint` (dark text of the same hue, stronger tint, set via `.chip[style*="--color-xxx"]`) because those bright colors aren't legible as text on light backgrounds. Layout: above 1500px the table sits beside two side-by-side panels (Asistencia | Registros), whose top is aligned with the table itself by `alignSidebar()` (sets `--align` on `.sidebar`; measured with `getBoundingClientRect` against `#viewGrid`, since Firefox treats the animating view as `offsetParent`); below that the panels drop under the table. Use `--accent-text`, not `--accent`, for amber text so it stays legible in day mode. Recessed areas inside elements (form fields, table break row) use `--inset`, not `--bg`, so changing the page background never recolors elements. The Asistencia/Registros boxes use `--panel` (= `--surface` in dark mode, a warm off-white `#f6eee2` in day mode instead of near-pure white), with `--bar-track` for the empty part of their bars and `--panel` for the 80 % tick. The "Trimestre" table has its own tokens (`--table-bg`, `--table-head`, `--table-holiday`): dark mode maps them to the surface tokens, and day mode uses a warm bone body with a caramel header band darker than `--bg` (keep them distinct from the page background).
- On touch devices (`pointer: coarse`) the page behaves like an app: no tap highlight, and no text selection or callout outside inputs.
- Fonts (Geist, Geist Mono) are bundled in `fonts/` (latin + latin-ext woff2, SIL OFL) and declared in `css/fonts.css`, so the app works offline; mono is only for times, dates, percentages and module codes.

There is no build, package manager, linter, or test suite. To run it, open `horario.html` in a browser or serve the directory (for example `python3 -m http.server`).

## Database design (`db/`, `docs/modelo-datos.md`)

A SQLite (≥ 3.37, `STRICT` tables) model for the whole CIFP, not yet used by the app: `db/schema.sql` (tables + triggers for rules SQLite can't express as `CHECK`: no overlapping classes per room/teacher/group, no classes in breaks or holidays, absences only for enrolled students, approving a justification marks absences justified), `db/views.sql` (`v_asistencia` / `v_asistencia_personal` reproduce `renderAttendanceBars()` over the whole course), and `db/seed_2asir.sql`, **generated** from the data tables of `js/script.js` by `node db/generar_seed.js` — rerun it whenever `MODULES`, `TIME_SLOTS`, `CALENDAR_DATES` or `SCHEDULE_A/B` change. `python3 db/pruebas.py` loads everything in memory and runs the checks (exit 1 on failure). Official absences (`falta`, teacher) and the student's own tracking (`falta_personal`) are separate tables; a class can belong to several groups (`sesion_grupo`; the current 2.º ASIR schedule has none shared, the tests create one), and 3 hours where A and B share Aula 235 are seeded with `aula_id` NULL ("por confirmar"). SQLite has no roles, so per-role access is the API's job: the permission matrix is in `docs/modelo-datos.md`.

## Android app (`android/`)

`android/build.sh` packages the web into `Horario.apk` (a single-Activity WebView loading `file:///android_asset/www/horario.html`) with plain SDK tools, no Gradle: it copies `horario.html`, `favicon.svg`, `css/`, `js/`, `fonts/` into assets, then runs aapt2, javac, d8, zipalign and apksigner. It expects JDK 17 under `~/.local/opt/jdk-17*` and `~/Android/Sdk` with `platforms;android-34` and `build-tools;34.0.0`. Rerun it after any web change; each run auto-increments the version code stored in `android/version.txt` so installs over the previous APK are treated as updates. The first run creates `android/horario-release.jks` + `keystore.properties`: updates must be signed with that same key, and neither file should be shared. The page calls `window.AndroidApp.setTheme(theme)` (when present) so the system bars follow the day/night theme; the Back button closes an open `<dialog>` or `#ctxMenu` before exiting. The only network use is the Campus (Moodle) integration, hence the INTERNET permission. Campus (Moodle, `api-integration` branch, first phase: read-only preview): the Consejería campus (`Moodle.SITE`, https://www3.gobiernodecanarias.org/medusa/eforma/campus) has the mobile web service on but logs in through CAS in a browser (`typeoflogin` 2) and sends no CORS headers, so everything network-related is native. `MainActivity.openMoodleLogin()` opens `admin/tool/mobile/launch.php?service=moodle_mobile_app&passport=…&urlscheme=moodlemobile` in a full-screen `Dialog` WebView and intercepts the `moodlemobile://token=` redirect; `Moodle.parseToken()` checks `md5(SITE + passport)` and the token stays in SharedPreferences (the page never sees it). The page calls `AndroidApp.moodleCall(id, fn, argsJson)` (a background thread POSTs to `webservice/rest/server.php`, only whitelisted read functions in `Moodle.ALLOWED`) and gets `moodleResult(id, json)` back; `moodleCall()` in `js/script.js` wraps that in a Promise and `flattenArgs()` turns arrays into PHP-style keys. The drawer's `.moodle-section` (only under `.is-app`) shows the account state right of its title (`#moodleState`, no box: «Conectado» in `--done` green with the class-in-progress `live-ping` dot, slowed to 2.4 s / «Sin conectar» with a hollow grey ring; `#moodleStatus` below only carries messages or the invitation to connect), only connects/disconnects (a single full-width button; the invitation reads «Vincula tu cuenta de Medusa para sincronizar tus tareas y actividades del campus.»). «Sincronizar» (`#moodleSyncBtn`, `.panel-sync`: a small ghost `.sync-btn` at the top right of the Registros panel head, only in the app with the account connected, `margin: -6px 0` so the head keeps its height) runs `moodleSync()` through the shared `btnBusy()`/`btnDone()` states («Sincronizando» → green «Sincronizado» → «Sincronizar»; errors also go to a toast, since the drawer is closed): site info → enrolled courses → `mod_assign_get_assignments` (kept only if its `duedate`, or `allowsubmissionsfromdate` when undated, falls in the school year from `MONTHS_DATA`: 1 Sep 2026 – 30 Jun 2027; courses left without assignments are hidden) → `mod_assign_get_submission_status` (4 at a time); strings from the server always go through `escapeHTML`. Course → subject mapping: `localStorage['horario_moodle_courses']` = `{ [Moodle course id]: { module: code | null, fullname, shortname, by: 'auto' | 'user' } }`, keyed by the stable course id (names are only shown and refreshed on rename; `null` = «Ninguna asignatura», never asked again). After fetching, `moodleSync()` keeps only courses with assignments in the school year and runs `resolveCourses()`: a saved mapping whose module still exists is reused; otherwise `autoModule()` tries only safe rules (exactly one `MODULES` code as a whole token of `shortname`/`idnumber`, e.g. `782NNS-IMW-2026_27`, or a fullname identical to the module name ignoring accents/case; zero or several matches → ask) and saves it as `auto`; what remains is asked in the same dialog (`renderCourseResolver()`, `data-mode="resolve"`, one `<select>` per course, «Continuar» = `saveCourseResolver()`, every course required) and then the list is shown. The Módulos header (no title; hidden on the web, where there is no campus) holds «Ajustes» and, to its right, «Actualizar», side by side; «Ajustes» (`openCampusCourses()`) reopens the resolver for every known course (built from the saved map, so it works offline; its button reads «Guardar», with «Cancelar»). `moduleOf(courseId)` is what placement and the list use. `renderMoodleList()` (`#moodleDialog`, «Pendientes en el campus») lists only the assignments still pending in the campus (not submitted, not graded) that are not in the app yet (`pendingAssigns()`; once added a row fades out with `record-out` and the list is rebuilt; when nothing is left to add the dialog shows only the title plus a green ✓ (its circle scales in with `empty-pop` and the tick then draws itself with `check-draw`, `pathLength="1"` + `stroke-dashoffset`, ~0.6 s; 18px above and below it) under the title «Nada nuevo por aquí…» (`renderMoodleRows()` sets it; «Pendientes en el campus» when there are rows) and «No hay tareas nuevas / para añadir a tu horario» (no final period) as two `display: block` spans (so the break keeps the normal line spacing), smaller and at 72 % of the text color; the dialog gets `data-empty` and centers its title too, and «Cerrar» becomes the primary button; the dialog has no «X» (Cerrar, backdrop or Back close it)), by due date (overdue in red): subject (`moduleOf()` chip + name, or the course name), task name, due date and an «Añadir tarea» button (`addMoodleTask(id, btn)`; none when undated). `placeMoodleTask()` writes a `task` with `moodle: <assign id>` (dedupe key), `title`/`text` from Moodle, `notify` [3] on first add: to `userEvents[idx]` if the due date is a class Wednesday where that module has a slot (`slot` = its first slot, `byDay: true`), otherwise to `personalEvents[iso]` of the due date with `module` (or, unmapped, the course name as `desc`). Every time the list opens, tasks already added are brought up to date (status done when submitted or graded, `grade` scaled to /10 when graded in points, moved if the due date changed), keeping your own fields (desc, weight, notify); `saveSlotRecord()` keeps `moodle` (and a personal record's `module`) when you edit one by hand. Only in the app with the account connected; on the web Módulos is unchanged. Background alerts: `MoodleWatch.java` schedules an inexact repeating alarm (~3 h, `MoodleWatchReceiver` with `goAsync()`), re-armed by `BootReceiver`. Each check fetches the courses' assignments dated inside the school year and compares them with a snapshot `{assign id → duedate}` in SharedPreferences via `CampusDiff.diff()` (pure Java, tested by `android/test/CampusDiffTest.java` with the plain JDK): new future assignments and changed due dates become one notification (grouped with InboxStyle when several) on the «Campus» channel; the first check only stores the snapshot. Tapping it opens the app with `openCampus`, which runs `moodleSync()`. The page keeps Java informed through `AndroidApp.moodleWatchState()` (`moodleWatchPush()`: enabled flag from `localStorage['horario_moodle_watch']`, school range, course→module map and, after «Sincronizar», the assignments already seen, which are merged into the snapshot so they are never announced). The Campus section only has «Conectar» or «Desconectar» (`.btn-danger`), full width in `.moodle-actions`; there is no manual «check now» button (the background check only runs on its alarm, and «Actualizar» in Módulos refreshes grades). Shared loading states for `.sync-btn` buttons: `btnBusy()` / `btnDone()` spin the `#i-sync` icon for at least 700 ms, optionally show a done label with a green ✓ `.is-done` for 2.4 s (`btn.doneTimer`, cleared if pressed again), and `setBtnLabel()` lowers the font only if a label overflows its fixed-width button; under reduced motion the icon pulses instead of spinning. «Desconectar» clears the watch and the cached grades. Reminders: `syncReminders()` (called from `saveData()` and `init()`) sends `AndroidApp.syncReminders(json)` the full list of pending exam/task reminders (`times` at the record's `notifyHour`, default `REMINDER_HOUR` 10, on each chosen day, and `due`), filtered by the «Notificaciones» preferences. Notificaciones (drawer section, only under `.is-app`): `localStorage['horario_notify']` = `{ exams, tasks, campusNew, campusMoved }` (`notifyPrefs()` merges `NOTIFY_DEFAULTS` and migrates the old `horario_moodle_watch` = '0'). Switches (`.switch-row`, `role="switch"`) turn exam/task reminders on or off; when to be warned is per record, not global; the Campus group (only when connected) toggles new-task and changed-date alerts, sent to `MoodleWatch` as `notifyNew`/`notifyMoved` (it still updates its snapshot when one is off). Every change goes through `saveNotifyPrefs()` → `syncReminders()` + `moodleWatchPush()`. If Android blocks the app's notifications (`AndroidApp.notificationsEnabled()`), `#notifyBlocked` offers «Permitirlas»; «Sonido y vibración» opens the app's notification settings (`AndroidApp.openNotificationSettings()`), and `onResume` re-renders the section. `Reminders.java` stores it in SharedPreferences and keeps one exact alarm per record, fired only on the chosen days (no daily repeat). The notification has "Posponer" (1 h) and, for tasks, "Entregada", which queues the id; the page picks the queue up with `applyNativeActions()` → `AndroidApp.takeDoneIds()` (on load and on `onResume`) and sets `status: 'done'`. `BootReceiver` reschedules after reboot or app update. Haptics: `haptic(kind)` in the page calls `AndroidApp.haptic()`, which plays Android's predefined effects (`tap` → `EFFECT_TICK` on a per-hour absence, `press` → `EFFECT_CLICK` when a long press opens the menu, `strong` → `EFFECT_HEAVY_CLICK` on a whole-day absence; one-shot fallback below API 29, `USAGE_TOUCH` from API 33 so the system touch-feedback setting applies); outside the app it falls back to a few ms of `navigator.vibrate` on touch screens.

## Data model (js/script.js)

These hardcoded tables are all aligned **by index**, so edits must keep them in sync:

- `CALENDAR_DATES`: one entry per Wednesday class date (39 entries). `monthIdx` is an index into `MONTHS_DATA` (0 = Sept 2026 … 9 = June 2027), **not** a JS month number. `dayNum` must match the day in `date`. Holiday entries carry `holiday`.
- `SCHEDULE_A` / `SCHEDULE_B`: parallel to `CALENDAR_DATES` (same length). Each entry is either `null` (no class or holiday) or a 5-element array of module codes, one per non-break slot in `TIME_SLOTS` (`key` 0–4). A slot can also be `null`.
- `MODULES`: module code → name, teacher, room, color. Every code used in the schedules must exist here and have a matching `--color-*` variable in `css/styles.css`.
- `MONTHS_DATA`: month grid metadata. `startDayOfWeek` is Monday-based (0 = Mon) and hand-computed; verify against `new Date()` when editing (all ten were once off by one).
- `userEvents`: user data persisted in `localStorage` under the key `academic_events_dark`, shaped as `{ [dateIndex]: [{ type: 'exam'|'task'|'absence'|'note', module, text, slot?, …typeFields }] }`. `slot` (a `TIME_SLOTS` key 0–4) is set only by clicking a chip in the "Trimestre" table (`toggleSlotAbsence()`); such an absence counts exactly 1 hour for its module. Clicking a date in the table header marks or clears all that day's hours at once (`toggleDayAbsence()`). Right-clicking a chip (or a ~480ms touch long-press, `startLongPress()`; the native `contextmenu` is ignored for touch and the release click is swallowed so it can't hit the menu) opens a custom context menu (`openSlotMenu()`; the same gesture on a table header date or a "Mes" day opens `openDayMenu()`, which asks for the kind and then the subject via `showModulePicker()`, and on a "Día" class row opens `openBlockMenu()`; `MENU_TARGETS` / `openMenuFor()` route contextmenu and long-press at document level; pressing the element whose menu is open only closes it, `onMenuOutside()` + `swallowNextClick()` drop that click) that creates per-hour `exam` (`examType` optional, one of `EXAM_TYPES` parcial/final/recuperacion/test, picked with single-select `.choice-chip` pills (all four on one row, sharing the width) that `chipDown()`/`chipClick()` let you untick; `recordLabel(ev)` shows it as «Examen parcial», «Recuperación»… in Registros, the Día list, the chip tooltip and the Android reminder text; `topics`, `weight` %, `grade` /10), `task` (`title`, `desc`, `weight`, `status` `'pending'|'done'`, `grade`; a graded task is always `done`: typing a grade checks «Entregada» and `saveSlotRecord()` enforces it) or `note` records via the `#slotDialog` form (`openSlotDialog()` / `saveSlotRecord()`); `text` always holds the one-line summary shown in lists. Exam/task records also carry a stable `id` (`newRecordId()`, assigned lazily to older records) and `notify` + `notifyDays` (days before, default `[3]`) + `notifyHour` (0–23, default 10; older records without it use 10) + `notifyMinute` (default 0), edited in the `.notify-fields` block of `#slotDialog`, which only shows inside the Android app (`html.is-app`): a «Notificar» switch (`#notifyOn`, off hides the rest), day chips rendered by `renderDayChips(days)` (presets `NOTIFY_PRESETS` 1/2/3/7/14 plus the record's own days; checkboxes, solid amber with a corner ✓ when ticked) with a dashed «+» (`startCustomDay()`) that turns into a text field (`inputmode="numeric"`, placeholder «Días» centered) for any 1–90 days (`commitCustomDay()` on Enter or blur), laid out in two columns: the day chips two per row on the left and, on the right, the time typed by hand in 12-hour format in a `.time-field` box made of two inputs (`#notifyTime` hours, `#notifyMin` minutes, numeric keyboard) with a fixed «:» between them in the placeholder grey: `timeHourInput()` jumps to the minutes after 2–9 or two digits (pasting «930» splits it), `timeMinInput()` turns 6–9 into «06»–«09», Backspace on empty minutes goes back (`timeMinKey()`), and leaving the box (`timeFieldOut()`) tidies it as «9:30» through `parseClock()`, which also takes 0 or 13–23 as 24-hour times that pick AM/PM themselves; `readNotifyTime()` / `setNotifyTime()` convert to and from 24 h; invalid → `notifyTime` error) with an AM | PM `.seg-radio` segmented control under it (`.ampm`, aligned with the second row of day chips). The whole «Notificar» block (its switch sits right next to the label) folds away with an animation (`.notify-fields` is a one-row grid, `grid-template-rows` 1fr → 0fr plus a fade, 280 ms, like the «i» help; `#slotDialog.no-notify`, `syncNotifyField()` on every input/change of the form) when `notifyApplies()` is false: the task is marked done, the record has a grade, or its date (`slotDue()`: class start, or 23:59 for personal days) has passed; the stored notify settings are kept, and `syncReminders()` likewise skips graded and past records. Weight and grade sit side by side at every width, each a `<label class="unit-field">` box whose input is sized to its text or placeholder (`fitUnitInput()`, in `ch` of the mono font, from `onSlotInput()` and on open) so value and unit read as one centered piece: «30%», «—/10» (unit in the placeholder grey) (`.field-row`, whose fields are subgrids so both boxes line up even when a label wraps). The head has the title with the type icon at its top right and the subject/date line under both, full width. `#slotDialog` has no «X» (Cancelar, Esc or the backdrop close it); the task Estado is a `.seg-radio` segmented control (radios inside the labels, the thumb follows the checked one through `:has()`, shared with the module status); its footer never wraps, like the module dialog's. Records created from the day menu carry `byDay: true`; exams with it (`isDayExam()`) put their dot on the day number (`dayDot()`, table header and "Mes" grid) instead of on the chip (`chipRecords()` excludes them). A dot turns green and stops pulsing when `recordsDone()` holds: every exam has a grade and every task is done (notes don't block it, but a notes-only chip stays yellow). Chips with any exam/task/note show a single pulsing yellow corner dot, and hovering (or keyboard focus) shows the `#chipTip` bubble listing those records (`showTip()`). Because events are keyed by position in `CALENDAR_DATES`, inserting or reordering dates silently reassigns existing user data to other dates.
- `personalEvents`: personal tasks and notes on days without classes (any "Mes" day not in `CALENDAR_DATES`, plus holidays and days whose schedule is empty), persisted separately in `localStorage['horario_personal']` as `{ 'YYYY-MM-DD': [{ type: 'task'|'note', text, title?, desc?, status?, id, notify?, notifyDays? }] }`, with no `module`, `slot`, `weight` or `grade` (except tasks imported from the campus, which may carry `module`, `grade` and `moodle`; Registros then shows the module chip instead of the «Personal» tag and their reminder carries the module code). `saveData()` persists both stores. In "Mes" those days are `button.month-day.is-free` (or class-less `CALENDAR_DATES` buttons) carrying `data-iso`; a mouse click or the context-menu gesture opens `openPersonalMenu()` (`hasClasses()` decides; on touch a plain tap does nothing, only the long press opens it), which edits through the shared `#slotDialog` via `openPersonalDialog()` (`showRecordDialog()` is the common part; `.is-personal` hides weight/grade and swaps `[data-personal]` labels to "Detalles"/"Hecha"). Up to three records are written inside the day cell (`personalList()`, hidden on phones where only `dayMarks()` remain). Registros merges them by date (`deletePersonal()`); in the table's sub-tabs a personal date belongs to the range that starts before it, up to the next range's first date. Personal tasks with `notify` are sent to Android too (`code: ''`, due 23:59; `Reminders.java` titles them "Entrega …" without a subject). Tasks there always belong to a subject and notes may: `modulesOn(iso)` lists the subjects whose teaching period (first to last class in the group's `getSchedule()`, excluding convalidated/withdrawn ones) contains that date, even if it is still in the future; `openPersonalMenu()` disables «Añadir tarea» when there are none. In `#slotDialog` (`.is-freeday`, the meta shows only the date, no «Personal» tag) `renderDayOwner()` builds `.day-owner`: for tasks a required «Asignatura» `.seg-radio` of those subjects (`#moduleSeg`, up to 4, with each subject's color dot; preselected when there is only one; error `moduleSeg`), and for notes first a «Personal | Clase» segmented control whose «Clase» unfolds the same picker (animated like «Notificar»; disabled when no subject is in its period). Records with a subject keep weight/grade and the class labels; the record's own subject is always offered (campus tasks).

Hardcoded date strings (`'23 Sep'`, `'13 Ene'`, `'20 Ene'`, `'28 Abr'`, `'5 May'`, `'16 Jun'`) define the three matrix sub-tab ranges in `renderMatrix()` and must match `CALENDAR_DATES[*].date` exactly. The button labels in `horario.html` read «1er/2º/3er trimestre» and repeat the dates only in their `title` tooltip.

## Rendering flow

State lives in globals (`currentGroup`, `selectedMonthIndex`, `selectedDateIndex`, `currentMatrixSubTab`, `filterModule`). Each view has a `render*()` function that rebuilds its container from scratch through `innerHTML`, so nothing is diffed. After any state change, call the render functions for the affected views:

- `saveData()` persists `userEvents` and re-renders every view that depends on events.
- The page has no title or search box: the header (`.topbar`) holds only the tabs and the menu button (`#menuBtn`), which opens `#menuDrawer`, a modal `<dialog>` sliding in from the right (`openMenu()` / `closeMenu()`, the latter runs the exit animation). It contains the group switch, the theme switch and the usage help.
- `switchGroup()` re-renders the views that depend on the schedule and saves the group in `localStorage['horario_group']`, read back on load (`loadGroup()`, `syncGroupLabels()`).
- `switchTab()` toggles `.is-shown` on `#viewMonthly`, `#viewWeekly`, `#viewGrid`, `#viewModules`, derives the tab button id as `'tab' + Capitalized(tab)`, and moves the sliding `.tab-indicator`.
- Full-screen table: `#fullBtn` (right end of `.grid-toolbar`) calls `openTableFull()`, which adds `html.table-full`: the same `.table-wrap` becomes `position: fixed` under `#fullBar` (exit and − / % / +, hidden on phones where pinch does it); the range selector itself is moved into `#fullBar` on open and back into `.grid-toolbar` on close, and `switchMatrixSubTab()` refits the new range while full, z-index 40 so toasts, the chip tooltip and the context menu stay above it. The committed zoom is CSS `zoom` on the table (real layout, so clicks, long presses and the sticky header/"Hora" column keep working); `fitTableFull()` measures it at zoom 1 and picks the zoom that shows the whole range (the minimum, shown as 100 %). Gestures never relayout per frame (that made the table shake as cells and glyphs re-rounded): the table sits in `#tableZoom`, a layer that `previewZoom()` scales with `transform` around the fixed point (`beginZoomGesture()`: cursor/fingers, or the center on an axis where the table will fit, re-decided on every wheel notch), clamped to positions the scroll can really reach; `commitZoom()` then applies the CSS zoom once and scrolls so the cell under the fixed point stays put (measured on the real cell, since zoom isn't perfectly proportional; far cells may settle a few px). Zoom by two-finger pinch (touch events; one-finger scrolling stays native), Ctrl + wheel / trackpad pinch (delta normalized for pixel/line/page modes, ~×1.16 per notch, fast spins accumulate) or the − / + buttons; wheel and buttons ease toward a target (`animateTableZoom()` / `stepTableZoom()`, 22 % of the remaining distance per frame); exit with the button, Esc or Android Back (`MainActivity.onBackPressed()` calls `closeTableFull()`).
- "Trimestre" (`viewGrid`) is the first tab and the default view. Its usage instructions are not shown inline but in the "Cómo se usa" section of `#menuDrawer`. `.hint-mouse` / `.hint-touch` spans swap the wording (clic / toca, clic derecho / mantén pulsada) under `(hover: none) and (pointer: coarse)`.
- On load, the selected date/month is the next upcoming class (`nextClassIndex()`), not the first date, and the table opens on the sub-tab containing it (`subTabOf()` / `setMatrixSubTab()`). On touch devices only, `scrollMatrixToToday()` (on load, after fonts load and on sub-tab change) scrolls `.table-wrap` so the first date column next to "Hora" is the last non-holiday class before today (measured as `offsetLeft` distance from the first date column, since the cells' `offsetParent` is the body); `switchTab()` keeps the table's `scrollLeft` when leaving and returning to "Trimestre".
- Live progress (`#liveClass`, under the "Trimestre" table): on a class day, `tickLive()` runs every second (`startLive()`, skipped while the page is hidden, rerun on `visibilitychange`) and `livePhase()` derives the current `TIME_SLOTS` segment from the clock: `class` (module color), `break`, `free` (null slot) or `done` (after the last class, 100 % in `--done` until `DAY_END` 23:59). It is hidden before the first class and on days without classes. The card is only rebuilt when the phase key changes; the fill advances via `--p` with a 1s linear transition. Entering `done` calls `celebrateDay()`, which runs `launchFireworks()` (a self-removing full-screen `<canvas class="fireworks">`, colors from the record/accent tokens, skipped under reduced motion) once per date, remembered in `localStorage['horario_fireworks']`; the "Otra vez" button replays it.
- Day numbers in the table header, the "Mes" grid and the "Día" tab (date list and `#selectedDateTitle`, via `.date-n`) are colored by state: the next class in amber (`is-next`), past class days in green (`is-past`, `--done`), and days where every class hour counts as an absence in red (`is-absent`, `--absence`, past or future; it wins over the other two). `dayState()` computes it.

Minimum attendance is per module: the gear in the Asistencia panel head (`.panel-btn`) opens `#limitDialog` (`openLimitDialog()` / `saveLimit()`, closed with the generic `closeDialog(id)`), listing exactly the modules shown in the panel at that moment (its `.att-row`s: trimester, month or day depending on the tab), with a 50–100 % input each; «Resetear» (`resetLimit()`) counts every input to 80 one unit at a time (rAF, at most one step per frame so no number is skipped, all finishing together in ≤ ~0.5 s, amber `.is-counting` text meanwhile); `finishReset()` completes a running count before saving or reopening, and a field typed into mid-count is left alone. `minAttendanceByModule` stores only the ones that differ from `DEFAULT_MIN` (80) in `localStorage['horario_min']` and `minAttendance(code)` reads it. Each module allows `floor(total × (100 − min) / 100)` absent hours, is `risk` below its minimum and `warn` within 10 points, and its bar tick sits at `--min` (set per `.att-row`). Attendance (`renderAttendanceBars()`): each module's total hours and absences are always counted over the whole course from the group's schedule (a module split across sub-tabs, like SOJ, must not jump to 0 % for one absence in the sub-tab where it has a single class); the current range (the table's sub-tab) only decides which modules are listed, those with a class in it. An absence tied to a module subtracts that module's slots for that day (or 2 if the module has none that day). An absence with no module subtracts one hour from every module scheduled that day. In the "Mes" tab it only lists the modules with a class in `selectedMonthIndex` (`changeMonth()` re-renders it, with an empty-state note for a month without classes). In the "Día" tab the panel only lists the modules scheduled on `selectedDateIndex` (percentages still count the whole course) and `selectDate()` re-renders it. `slotAbsence()` tells the table whether a cell is covered by a per-hour absence (toggleable) or by one of these broader ones (click only shakes and shows a toast).

The Módulos list has no column header row and the tab has no title; a 2px `--line-strong` rule tops the list. Per-module settings (Módulos, «⋯» button `.module-more` on each row → `#moduleDialog`, `openModuleDialog()` / `saveModuleDialog()`, one accent only: «Guardar» is the sole colored action, «Cancelar» ghost, and «Restablecer» (`resetModuleDialog()`) a neutral ghost button with a 14px undo icon at the bottom-left corner of the footer, opposite «Guardar»; the three footer buttons never wrap (`nowrap`, font `min(0.8125rem, 3.5vw)`, padding `clamp(8px, 2.6vw, 12px)`, so they fit at 320px and with large system fonts); pressing it flashes green with a ✓ for 2.4 s (`flashDone(btn, icon)`, the same `.sync-btn.is-done` look and `sync-done` pop as «Actualizado»), reset each time the dialog opens. Docente and Aula are read-only data rows (`.info-row`: label · value · pencil `.edit-btn`); `editField(id)` makes the input editable (boxed, amber border, text selected) and `stopEditField()` on blur turns it back into plain text. Estado is the same `.segmented` control as Grupo/Tema (`#moduleStatus`, neutral thumb, radios inside the labels, `syncStatusSeg()` sets `data-active`; labels capped at `min(0.8125rem, 3.7vw)`); its explanation is folded behind an «i» button next to «Estado» (`.info-btn` + `.info-reveal`, `toggleInfo(btn, open?)` flips `aria-expanded` and animates `grid-template-rows` 0fr → 1fr; closed again each time the dialog opens); on phones the dialog padding drops to 20px): `localStorage['horario_modules']` = `{ code: { teacher?, room?, status? } }` keeps only what differs from `MODULES`; `teacherOf(code)` / `roomOf(code)` (null = no room) are what the Día rows and Módulos show. `status` `'convalidada' | 'desistida'` removes the module from `getSchedule()` (cached per group + excluded set; a day left with no class becomes `null`), so the table, Día, Mes, Asistencia, live progress, campus placement and reminders (`syncReminders()` also skips records of excluded modules) all drop it, while its records stay stored; in Módulos the row stays, dimmed (`.is-off`) with a `.module-state` tag and no hours, so it can be restored. On phones (≤900px) teacher and room are one line «docente – aula» (`.module-where`; desktop keeps their columns). `filterModule` is always `null` since the search box was removed; renderers still add `.is-dimmed` to anything that isn't that module when it is set.

The Registros panel lists the events of the current range (the table's sub-tab range on "Trimestre", all dates elsewhere). Its three filter tiles call `setRecordFilter('exam'|'task'|'note')`, which sets `recordFilter` so `renderSidebarNotes()` shows only that type; pressing the active one again resets it to `null` (show everything, absences included). Rows must not move when the filter changes: every `.record` has the same padding (the first only gets a transparent top border) and the filter swap only fades rows in (`fade-in`, no translate). Per-hour absences stay one event per slot in storage, but `groupDayEvents()` shows 2+ consecutive slots of the same day (the break doesn't split a run) as one entry, "Falta del día" when it covers every class slot and "Faltas seguidas" otherwise, listing each module with its session count and no times; its delete button removes the whole run (`deleteEvents()`). The "Día" view's event list uses the same grouping. On phones (≤720px) that list (`#dayEvents`) is hidden and on "Trimestre", "Mes" and "Día" (not "Módulos") the Registros panel moves above Asistencia (CSS `order` via `.layout:has(:is(#viewGrid, #viewMonthly, #viewWeekly).is-shown)`). There each class row (`.slot`) is regridded with `display: contents` on `.slot-body`/`.slot-text`: the subject name gets the whole first line beside the chip, and under it teacher · room plus `.slot-count` (hidden on desktop, where `.slot-dur` follows the name) with the time at their right. Each Registros row shows the date large and bold on the left as `7 SEP` (`recordDate()`), with the subject chip (or the "Personal" tag) under it; `.record-when` is a two-row grid sharing `--rec-row`/`--rec-gap` with `.record-head` and the first line of `.record-text`, so the date lines up with the type and the chip with the text; to the right, a `.record-head` line with the type (`recordMeta(label)`) followed by `— Pendiente`/`— Entregada` for tasks or `— Nota x` for graded exams (`recordStatus()`, green when done), then the comment and a detail line with weight and task grade (`recordExtra()`), with no times; a single per-hour absence reads "1 sesión" instead of its stored `Hora …` text. The panel has no add button: records are created from the table, so the `#eventModal` add form is no longer reachable from the UI.

## Motion

- Entrance animation plays once per page load: an inline `<head>` script adds `html.is-intro` (skipped under `prefers-reduced-motion`), CSS keys the intro keyframes off it, and `init()` removes it after 1.5s. Content is visible by default if JS fails.
- Re-renders replace `innerHTML`, so state-change animations are re-triggered with `replay(el, 'is-swapping')`. Attendance bars keep their previous `--p` for one frame so width changes animate via `transform: scaleX`.
- The add-record form is a native `<dialog>`; close through `closeAddModal()` so the exit animation runs.
- Dialog scrollbars only show while scrolling: a capture `scroll` listener adds `.is-scrolling` to the enclosing `dialog` and removes it after 1 s idle; the color is the registered `@property --sb` used in `scrollbar-color` for `dialog, dialog *`, so it fades (120 ms in, 360 ms out).
- While any modal `<dialog>` is open (dialogs and the side menu) the page behind can't scroll: `html:has(dialog:modal) { overflow: hidden }`, and every `dialog` has `overscroll-behavior: contain` so reaching its end doesn't chain the swipe to the page.
